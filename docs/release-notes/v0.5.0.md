# datagrant v0.5.0

> Ready, release pending. Not tagged or published yet. The maintainer tags.

**Ops hardening for datagrant's just-in-time, masked Postgres access.**

## Highlights

- **Advisory lock.** Mutating `--apply` takes a session `pg_advisory_lock` on `DATAGRANT_ADVISORY_LOCK_KEY` (`0x64677401`) before the live-grant count. `request` / `approve` / `preflight --apply` wait up to 30s, then fail closed (exit 3, no grant) if another session still holds the key. `revoke` / `sweep` use `pg_try_advisory_lock` and proceed without the lock if it is busy (they warn with the holding pid(s)). Dry runs do not lock. `PUBLIC` can `EXECUTE pg_advisory_lock`; the lock is a coordination aid, not a security boundary.
- **`datagrant doctor`.** Read-only host and database checks: keys, policy parse, POSIX file modes, DSN, PUBLIC preflight, `pg_signal_backend`, ability to `SET log_statement` (without issuing SET), receipt-log chain, optional sink cursor. Exit 0/1/2. Warnings do not fail. No `--apply`, no schemas, keys, or grants, no advisory lock.
- **`strict_preflight`.** Optional. Omit or `false` keeps PUBLIC warnings and still grants. `true` means `--apply` on `request`, `approve`, and `preflight` exits 1 when those PUBLIC defaults remain. `preflight --apply` still creates datagrant state before refusing. `revoke` and `sweep` never refuse for this reason.
- **POSIX file modes.** A group/other-accessible receipt log is refused on access-creating `--apply`; `revoke` / `sweep` warn, still revoke, and exit 3. Policy-file mode warns by default (`group/other-accessible`; writable is the stronger finding). Optional `strict_policy_permissions` refuses access-creating `--apply` only. Extra warnings when the file is not owned by the current user or the parent directory is group/other-writable. FIFO/socket paths are rejected before `open`.
- **`--strict-policy-permissions` / `$DATAGRANT_STRICT_POLICY_PERMISSIONS`.** Force the policy-file mode check from outside the file. On access-creating `--apply` and `doctor`, a group/other-accessible policy is refused after a hostfs inspect and before the YAML is parsed. The in-file key is still defeated by write access. Unset/empty/`0`/`false`/`no`/`off` is off; `1`/`true`/`yes`/`on` is on. Any other non-empty value is exit 2 on access-creating `--apply` and `doctor` only; `revoke` and `sweep` do not parse the variable.
- **`SET LOCAL log_statement = 'none'`.** `apply_plan` and two-person `create_request` issue it in the grant/request transaction when the admin can SET that GUC (superuser, or PostgreSQL 15+ `GRANT SET ON PARAMETER log_statement`). `request` / `approve --apply` refuse if it cannot. `revoke` / `sweep` proceed without SET. Doctor reports the privilege and never SETs. Residual: `log_min_duration_statement = 0` and `log_min_error_statement` can still capture parameters or a failed `CREATE ROLE` verifier.
- `make demo` omits `strict_preflight` and `strict_policy_permissions` and does not walk `datagrant doctor`.

## Upgrading

1. There is no hash-output break in this version. The v0.2.0 per-dataset `hash_scope` change from v0.1.0 still applies if you are coming from 0.1.x; see [v0.2.0 notes](v0.2.0.md).
2. Install from source (`pip install .` in this checkout). datagrant is not on PyPI. A v0.5.0 tag is not published yet. [v0.4.0](https://github.com/chriswayneh/datagrant/releases/tag/v0.4.0) remains the latest published release.
3. Existing keys, policies, receipt logs and state schemas keep working. Policies that omit `strict_preflight` and `strict_policy_permissions` parse and evaluate as in v0.4.0. `receipts verify` still accepts v0.4.0 logs.
4. Optional: add `strict_preflight` and/or `strict_policy_permissions`, grant `SET` on `log_statement` to the admin role, and run `datagrant doctor` before `--apply`. See [policy](../policy.md), [CLI](../cli.md), [operations](../operations.md#ops-hardening-v050) and the [design](../design/ops-hardening.md). Check with `datagrant policy check`.
5. Grant `SET` on `log_statement` (or run as superuser) before `request` / `approve --apply`. Without it, those commands refuse (exit 1). `revoke` and `sweep` still run.

## Requirements

Python 3.11+, Postgres (CI tests 16), and `pgcrypto` for hash masks. No new dependencies.

## Known limits

- Local identity is not authentication: `--as-user` and OS user names are not verified. In `identity.mode: local`, `approvals_required` is N claimed names and `distinct-groups` is only as strong as the claimed names.
- OIDC is a CLI boundary, not a database boundary. Anyone who holds the admin DSN can still bypass datagrant. Locks, doctor, and strict preflight are workflow and host controls unless datagrant runs on a bastion that holds `DATAGRANT_DSN`.
- The advisory lock is not a security boundary. `PUBLIC` can `EXECUTE pg_advisory_lock`, so a grant role or any other CONNECT role can hold the key and stall access-creating `--apply` until the 30s timeout. It cannot stall `revoke` / `sweep`.
- In-file `strict_policy_permissions` is defeated by write access to the policy file. Use `--strict-policy-permissions` or `$DATAGRANT_STRICT_POLICY_PERMISSIONS` to force the check from outside the file.
- Residual statement logging: a superuser or server-wide collector with `log_min_duration_statement = 0` can still capture hash-key parameters and SCRAM verifiers. `log_min_error_statement` (default `error`) still logs the full text of a failing statement, so a failed `CREATE ROLE` can log its verifier literal.
- Bearer ID tokens can be replayed until `exp` and `max_token_age`. There is no DPoP or live IdP session revocation.
- A revoked IdP signing key remains accepted until `jwks_cache_ttl` (default `5m`).
- Unmapped IdP groups grant nothing, even when the name matches a policy group.
- `http://` localhost issuers need `DATAGRANT_OIDC_ALLOW_INSECURE_LOCALHOST=1` and are for tests only.
- Short DSN passwords (1-3 characters) can still appear as bare substrings in messages; URI and `password=` forms are always stripped.
- Hashes are still linkable within one scope, and anyone with the hash key file can recompute them.
- A grantee knows every visible row matched the filter, even on a hidden filter column.
- NULL stays NULL under `partial` and `hash`; `partial` keeps the length.
- Receipts not yet delivered to the sink can't be checked off-host; in `best-effort` mode they can be deleted before `receipts push` runs. The sink is only as trustworthy as its receiver.
- The sink token lives in the environment.
- On Windows, the receipt log, the file sink and outbox flushes aren't locked; run one writer at a time.
- Symlinks are refused for the final path component of key, log, cursor and sink files, but parent directories are followed.
- Denial receipts grow the log. Only `--apply` writes them. Reasons are policy text, never row values or passwords.
