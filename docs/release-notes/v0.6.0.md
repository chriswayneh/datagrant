# datagrant v0.6.0

> Ready, release pending. Not tagged or published yet. The maintainer tags.

**Snowflake warehouse support for datagrant's just-in-time, masked access.**

## Highlights

- **Dataset `engine`.** Optional `postgres` (default, including omitted) or `snowflake`. Unknown strings and a table-level `engine` are policy errors. Omitting `engine` on every dataset is v0.5.0. Mixed files parse (`datagrant policy check`). `policy.version` stays `1`.
- **Snowflake `--apply` routing.** Requires the extra `datagrant[snowflake]` (`pip install 'datagrant[snowflake]'`, `snowflake-connector-python>=4.7.3,<6`) and `--snowflake-dsn` / `$DATAGRANT_SNOWFLAKE_DSN` (service user, `private_key_file`; password auth is refused). Prefer the env var over the flag. Postgres `--apply` does not read Snowflake settings or import the extra. CI does not call Snowflake.
- **Per-grant `TYPE=SERVICE` user.** RSA key pair shown once (private key to stdout, public key only in SQL, fingerprint on the `issued` receipt). Fail-safe order: `issuing` row, DISABLED user, secure view, role, receipt, claim `issuing` to `enabling`, ENABLE, then `active` from `enabling`. Reverse-drop on failure.
- **Revoke and sweep.** `ALTER USER IF EXISTS ... SET DISABLED = TRUE` (DISABLE aborts queries), then `DROP VIEW` / `ROLE` / `USER IF EXISTS`. A DISABLE error is `revoke_failed` / exit 4. Sweep every 1 minute. Skip `issuing`/`enabling` rows younger than 10 minutes. Pending TTL expiry does not drop Snowflake objects.
- **Masks and catalog.** The same five mask names as Postgres. `--apply` reads types from `INFORMATION_SCHEMA.COLUMNS`. `null` is `CAST(NULL AS <type>)`. Secure views alias the source as `FROM db.s.t AS "SRC"` and qualify filter and source columns as `"SRC"."COL"`, so an `IS NULL` filter on a `null`-masked column uses the base column. View DDL has no hash-key bytes.
- **Hashes.** Snowflake HMAC output is not designed to be joinable with a Postgres hash of the same value (different HMAC output encoding). Keep separate `hash_scope` values.
- **Concurrent cap.** Counted per engine. Snowflake counts `issuing`/`enabling`/`active` across all Snowflake datasets. Postgres grants do not count against the Snowflake cap, and the reverse is also true.
- `make demo` stays Postgres.

## Upgrading

1. There is no hash-output break for Postgres in this version. The v0.2.0 per-dataset `hash_scope` change from v0.1.0 still applies if you are coming from 0.1.x; see [v0.2.0 notes](v0.2.0.md). Snowflake hashes are not designed to be joinable with Postgres hashes (different HMAC output encoding).
2. Install from source (`pip install .` in this checkout). For Snowflake, `pip install '.[snowflake]'`. datagrant is not on PyPI. A v0.6.0 tag is not published yet. [v0.5.0](https://github.com/chriswayneh/datagrant/releases/tag/v0.5.0) remains the latest published release.
3. Existing keys, policies, receipt logs and Postgres state schemas keep working. Policies that omit `engine` parse and evaluate as in v0.5.0. `receipts verify` still accepts v0.5.0 logs.
4. Optional: add `engine: snowflake` datasets, set `$DATAGRANT_SNOWFLAKE_DSN`, and schedule `datagrant sweep --apply` every 1 minute. See [policy](../policy.md), [CLI](../cli.md), [operations](../operations.md#warehouses-v060) and the [design](../design/warehouses.md). Check with `datagrant policy check`.

## Requirements

Python 3.11+, Postgres (CI tests 16), and `pgcrypto` for Postgres hash masks. Snowflake is an optional extra (`snowflake-connector-python>=4.7.3,<6`). No live Snowflake in CI.

## Known limits

- Local identity is not authentication: `--as-user` and OS user names are not verified. In `identity.mode: local`, `approvals_required` is N claimed names and `distinct-groups` is only as strong as the claimed names.
- OIDC is a CLI boundary, not a database boundary. Anyone who holds the admin DSN (Postgres or Snowflake) can still bypass datagrant.
- Sub-day Snowflake expiry is sweep, not `DAYS_TO_EXPIRY`. Missed sweeps leave the grant user ENABLE until the next successful sweep.
- `issuing`/`enabling` grace is 10 minutes. Sweep will not drop those rows while they are in grace.
- Snowflake hashes are not designed to be joinable with Postgres hashes (different HMAC output encoding).
- Bearer ID tokens can be replayed until `exp` and `max_token_age`. There is no DPoP or live IdP session revocation.
- A revoked IdP signing key remains accepted until `jwks_cache_ttl` (default `5m`).
- Unmapped IdP groups grant nothing, even when the name matches a policy group.
- `http://` localhost issuers need `DATAGRANT_OIDC_ALLOW_INSECURE_LOCALHOST=1` and are for tests only.
- Short DSN passwords (1-3 characters) can still appear as bare substrings in messages; URI and `password=` forms are always stripped.
- Hashes are still linkable within one scope, and anyone with the hash key file can recompute them.
- A grantee knows every visible row matched the filter, even on a hidden filter column.
- NULL stays NULL under `partial` and `hash`; `partial` keeps the length.
- Receipts not yet delivered to the sink can't be checked off-host; in `best-effort` mode they can be deleted before `receipts push` runs. The sink is only as trustworthy as its receiver.
- The sink token lives in the environment.
- On Windows, the receipt log, the file sink and outbox flushes aren't locked; run one writer at a time.
- Symlinks are refused for the final path component of key, log, cursor and sink files, but parent directories are followed.
- Denial receipts grow the log. Only `--apply` writes them. Reasons are policy text, never row values or passwords.
