# datagrant v0.4.0

> Ready, release pending. Not tagged or published yet. The maintainer tags.

**Approvals and policy limits for datagrant's just-in-time, masked Postgres access.**

## Highlights

- **Policy limits.** Optional `pending_ttl` (`1m`..`7d`) caps an explicit `request --pending-ttl` in two-person mode (exit 2 if the flag is longer; omitted flag uses `min(24h, policy.pending_ttl)`). Per-table `max_columns` denies a request whose unique column count exceeds it (cannot exceed the size of `columns`). `max_concurrent_grants` is policy-wide and/or per dataset (minimum of those set); the count is `status = 'active' AND expires_at > now()` for that requester on `request` and `approve`. Revoked grants and grants past `expires_at`, swept or not, do not count. Omitting the keys keeps v0.3.0 behavior. `policy.version` stays `1`.
- **Policy-wide quorum.** Optional `approvals_required` (integer 1..8, default 1) on `approval: two-person` only. A pending request issues only after N distinct approvers. Votes are stamped with `policy.sha256`, OIDC `iss`, and the voter's `mapped_groups`. Counting uses those stored groups with `can_approve`, so a `group_map`-only approver reaches quorum. A second vote from the same person (name, or OIDC `(iss, sub)`) is idempotent and replaces a stored row that no longer counts. Partial `--apply` votes write `approval_recorded` from the counted votes only. The Nth vote and the grant commit in `apply_plan`'s transaction first; the `issued` receipt runs after that commit. If the locked counted names do not match the plan's approvers, apply fails closed, rolls back, and the request stays pending.
- **Separation of duties.** Optional `separation_of_duties: distinct-groups` refuses approve when (requester groups ∩ approver groups ∩ the table's `allowed_groups`) is non-empty. Default `none`. Groups are static `policy.groups` plus OIDC `group_map` extras. It does not replace distinct-person / `(iss, sub)`.
- **Denial and expiry receipts, `--apply` only.** `denied` on a refused `request --apply`; `not_approved` on a refused `approve --apply`; `request_expired` when `sweep --apply` expires a pending request. Dry runs write nothing. Receipts stay version 1. `grant_id` is omitted. A `denied` / `not_approved` / `approval_recorded` receipt that cannot be written is exit 3 and creates no pending row or grant (a failed `approval_recorded` write removes that caller's vote). Sweep still expires the pending row if `request_expired` cannot be written.
- There is no break-glass key. Emergency access is a reviewed policy edit to `approval: auto`.
- `make demo` stays local two-person with one approver. It does not walk quorum N>1, `distinct-groups`, or the new limit keys.

## Upgrading

1. There is no hash-output break in this version. The v0.2.0 per-dataset `hash_scope` change from v0.1.0 still applies if you are coming from 0.1.x; see [v0.2.0 notes](v0.2.0.md).
2. Install from source (`pip install .` in this checkout). datagrant is not on PyPI. A v0.4.0 tag is not published yet.
3. Existing keys, policies, receipt logs and state schemas keep working. Policies that omit every new key parse and evaluate as in v0.3.0 (`approvals_required` 1, no extra SoD, no concurrent cap, no `max_columns`, pending TTL default 24h). `receipts verify` still accepts v0.3.0 logs.
4. Optional: add `approvals_required`, `separation_of_duties`, `pending_ttl`, `max_concurrent_grants`, and per-table `max_columns`. See [policy](../policy.md), [CLI](../cli.md), [operations](../operations.md#approvals-and-policy-limits-v040) and the [design](../design/approvals-policy-limits.md). Check with `datagrant policy check`.
5. Dataset-level `approvals_required` is a policy load error. Unknown `separation_of_duties` strings are errors.

## Requirements

Python 3.11+, Postgres (CI tests 16), and `pgcrypto` for hash masks. No new dependencies.

## Known limits

- Local identity is not authentication: `--as-user` and OS user names are not verified. In `identity.mode: local`, `approvals_required` is N claimed names and `distinct-groups` is only as strong as the claimed names.
- OIDC is a CLI boundary, not a database boundary. Anyone who holds the admin DSN can still bypass datagrant. Limits, quorum and SoD are workflow controls unless datagrant runs on a bastion that holds `DATAGRANT_DSN`.
- Two `auto --apply` writers can both pass the live-grant count and both insert. The documented ops model is one writer.
- Bearer ID tokens can be replayed until `exp` and `max_token_age`. There is no DPoP or live IdP session revocation.
- A revoked IdP signing key remains accepted until `jwks_cache_ttl` (default `5m`).
- Unmapped IdP groups grant nothing, even when the name matches a policy group.
- `http://` localhost issuers need `DATAGRANT_OIDC_ALLOW_INSECURE_LOCALHOST=1` and are for tests only.
- Short DSN passwords (1-3 characters) can still appear as bare substrings in messages; URI and `password=` forms are always stripped.
- Hashes are still linkable within one scope, and anyone with the hash key file can recompute them.
- A grantee knows every visible row matched the filter, even on a hidden filter column.
- NULL stays NULL under `partial` and `hash`; `partial` keeps the length.
- Receipts not yet delivered to the sink can't be checked off-host; in `best-effort` mode they can be deleted before `receipts push` runs. The sink is only as trustworthy as its receiver.
- The sink token lives in the environment.
- On Windows, the receipt log, the file sink and outbox flushes aren't locked; run one writer at a time.
- Symlinks are refused for the final path component of key, log, cursor and sink files, but parent directories are followed.
- Disable statement logging for the admin role.
- Denial receipts grow the log. Only `--apply` writes them. Reasons are policy text, never row values or passwords.
