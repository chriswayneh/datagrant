# datagrant v0.7.0

> [Released on GitHub](https://github.com/chriswayneh/datagrant/releases/tag/v0.7.0) on 2026-11-21. Mock- and CI-tested. A live GCP test was not run.

**BigQuery warehouse support for datagrant's just-in-time, masked access.**

## Highlights

- **Dataset `engine`.** Optional `postgres` (default, including omitted), `snowflake`, or `bigquery`. Unknown strings and a table-level `engine` are policy errors. Mixed files parse (`datagrant policy check`). `policy.version` stays `1`.
- **BigQuery `--apply` routing.** Requires the extra `datagrant[bigquery]` (`pip install 'datagrant[bigquery]'`) and `$DATAGRANT_BIGQUERY_PROJECT` / `--bigquery-project`. Operator auth is Application Default Credentials. JSON key files, `credentials_path`, and `--bigquery-dsn` are refused. Prefer the env var over the flag. Postgres and Snowflake `--apply` do not read BigQuery settings or import the extra.
- **Identity binding.** The Google principal comes from `policy.identity.google_principals`, then a verified OIDC email when `username_claim` is `email`. `--google-principal` may only confirm that bound value. Two-person `request --apply` stores the principal only; `approve --apply` issues from that stored value.
- **Authorized view plus IAM.** Per-grant view `G_<id>` in shared `datagrant_views`. Fail-safe order: `issuing` row, view, authorize `datagrant_views` on the source only if missing, receipt, claim `issuing` to `enabling`, IAM last, then `active`. Reverse-drop on failure. Custom grantee role is `bigquery.tables.getData` only (no `tables.get`).
- **Revoke and sweep.** Drop the view first, then that grant's dataset bind and `jobUser` bind. A view-drop error is still `revoke_failed` / exit 4 after IAM removal is attempted. Sweep every 1 minute. Skip `issuing`/`enabling` rows younger than 10 minutes. Pending TTL expiry does not drop BigQuery objects. IAM `request.time` is a backstop for new queries, not a substitute for sweep.
- **Masks and catalog.** The same five mask names as Postgres and Snowflake. `--apply` reads types from `INFORMATION_SCHEMA.COLUMNS` in the **source** project (case-insensitive column matching). `null` is `CAST(NULL AS <type>)`. Views alias the source as `` `SRC` `` and qualify filters as `` `SRC`.`COL` ``. View DDL has no hash-key bytes.
- **Hash setup.** `datagrant setup bigquery` (dry run by default; `--apply` to provision) writes `datagrant._hash_master` with a load job, never a query parameter. An existing row is fingerprint-compared (`TO_HEX(SHA256(key)) = @fp`). `--rotate-hash-key` prints the live hash-grant count and refuses while any are active unless `--force`. Rotation changes every BigQuery pseudonym and can `WRITE_TRUNCATE` duplicate master rows. The `datagrant` dataset must be operator-only. Project-level BigQuery data roles are key-equivalent; use a dedicated hash project.
- **Hashes.** BigQuery and Postgres hashes of the same value under the same `hash_scope` are identical, and Snowflake's are the same value in uppercase. Use distinct `hash_scope` values per engine when hashes must not link.
- **Concurrent cap.** Counted per engine. BigQuery counts `issuing`/`enabling`/`active` across all BigQuery datasets of that store. Postgres and Snowflake grants do not count against the BigQuery cap, and the reverse is also true.
- `make demo` stays Postgres.

This release is **mock- and CI-tested**. A live GCP test was not run. Optional live tests stay behind `DATAGRANT_TEST_BIGQUERY`.

## Upgrading

1. There is no hash-output break for Postgres or Snowflake in this version. The v0.2.0 per-dataset `hash_scope` change from v0.1.0 still applies if you are coming from 0.1.x; see [v0.2.0 notes](v0.2.0.md). BigQuery and Postgres hashes of the same value under the same `hash_scope` are identical, and Snowflake's are the same value in uppercase. Use distinct `hash_scope` values per engine when hashes must not link.
2. Install from source (`pip install .` in a checkout of the v0.7.0 tag). For BigQuery, `pip install '.[bigquery]'`. For Snowflake, `pip install '.[snowflake]'`. datagrant is not on PyPI.
3. Existing keys, policies, receipt logs, Postgres state schemas, and Snowflake state keep working. Policies that omit `engine` parse and evaluate as in v0.6.x. `receipts verify` still accepts v0.6.x logs.
4. Optional: add `engine: bigquery` datasets, set `$DATAGRANT_BIGQUERY_PROJECT`, run `datagrant setup bigquery --apply` against an operator-only `datagrant` dataset (dedicated hash project recommended), and schedule `datagrant sweep --apply` every 1 minute. See [policy](../policy.md), [CLI](../cli.md), [operations](../operations.md#bigquery-v070) and the [design](../design/bigquery.md). Check with `datagrant policy check`.

## Requirements

Python 3.11+, Postgres (CI tests 16), and `pgcrypto` for Postgres hash masks. Snowflake is an optional extra (`snowflake-connector-python>=4.7.3,<6`). BigQuery is an optional extra (`google-cloud-bigquery>=3.27.0,<4`). No live Snowflake or BigQuery in CI.

## Known limits

- Local identity is not authentication: `--as-user` and OS user names are not verified. In `identity.mode: local`, `approvals_required` is N claimed names and `distinct-groups` is only as strong as the claimed names.
- OIDC is a CLI boundary, not a warehouse boundary. Anyone who holds the admin DSN (Postgres or Snowflake) or ADC for the grant project can still bypass datagrant.
- Sub-day BigQuery expiry is sweep plus an IAM `request.time` backstop. Missed sweeps leave the view until the next successful sweep.
- `issuing`/`enabling` grace is 10 minutes. Sweep will not drop those rows while they are in grace.
- BigQuery and Postgres hashes of the same value under the same `hash_scope` are identical, and Snowflake's are the same value in uppercase. Use distinct `hash_scope` values per engine when hashes must not link.
- Hash preflight is a snapshot. Between that check and the first `hash_hmac` call, dataset ACL or project IAM can change. Re-run `datagrant setup bigquery` and `policy check` after ACL or IAM edits.
- Project-level BigQuery data roles (`roles/bigquery.dataViewer` and stronger) on the hash project are key-equivalent.
- A missing authorized-routine ACL is not a grant-time failure: the grant can be `active` and the view unusable.
- Bearer ID tokens can be replayed until `exp` and `max_token_age`. There is no DPoP or live IdP session revocation.
- A revoked IdP signing key remains accepted until `jwks_cache_ttl` (default `5m`).
- Unmapped IdP groups grant nothing, even when the name matches a policy group.
- `http://` localhost issuers need `DATAGRANT_OIDC_ALLOW_INSECURE_LOCALHOST=1` and are for tests only.
- Short DSN passwords (1-3 characters) can still appear as bare substrings in messages; URI and `password=` forms are always stripped.
- Hashes are still linkable within one scope, and anyone with the hash key file can recompute them.
- A grantee knows every visible row matched the filter, even on a hidden filter column.
- NULL stays NULL under `partial` and `hash`; `partial` keeps the length.
- Receipts not yet delivered to the sink can't be checked off-host; in `best-effort` mode they can be deleted before `receipts push` runs. The sink is only as trustworthy as its receiver.
- The sink token lives in the environment.
- On Windows, the receipt log, the file sink and outbox flushes aren't locked; run one writer at a time.
- Symlinks are refused for the final path component of key, log, cursor and sink files, but parent directories are followed.
- Denial receipts grow the log. Only `--apply` writes them. Reasons are policy text, never row values or passwords.
- A live GCP test was not run for this release.
