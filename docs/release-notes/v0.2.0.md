# datagrant v0.2.0

> Released 2026-11-04: [v0.2.0 on GitHub](https://github.com/chriswayneh/datagrant/releases/tag/v0.2.0).

**Tighter privacy controls and off-host evidence for datagrant's just-in-time, masked Postgres access.**

## Highlights

- **Per-dataset hash scope.** `hash` masks use a key derived for each dataset (`hash_scope`, default the dataset name), so equal values no longer match across datasets. Datasets that set the same `hash_scope` still share hashes on purpose.
- **`filter_columns`.** A row filter can use a column that is never in the grant view and can't be requested, for example filtering on `region` without exposing it.
- **External receipt sink.** Every receipt can also go to an HTTPS webhook (standard library only, token from `DATAGRANT_RECEIPT_SINK_TOKEN`) or an append-only `file://` sink.
  - `best-effort` mode (default) warns and keeps undelivered receipts in an outbox; `required` mode revokes a grant whose `issued` receipt can't be delivered. Revokes never wait on the sink.
  - `receipts push` sends pending receipts after an outage (dry run unless `--apply`).
  - `receipts verify --sink` compares the local chain with the sink head and catches a truncated or rewritten local log without a hand-recorded head hash.

## Breaking change: hash outputs

Hashed values from v0.1.0 grants won't match v0.2.0 grants, and values from different datasets won't match each other. Anything that joins on hashed values across versions or across datasets will stop matching. There is no switch back to the single unscoped key. If you need old and new outputs to agree, re-issue the old grants under v0.2.0.

## Upgrading

1. Read the breaking change above and check whether anything downstream joins on `hash` outputs.
2. Install the new version from source (`pip install .` in a checkout of the v0.2.0 tag). datagrant is not on PyPI.
3. Existing keys, policies, receipt logs and state schemas keep working. Run `datagrant preflight --apply` once.
4. Optional: add `hash_scope` to datasets that must share hashes, and `filter_columns` where a filter column shouldn't be visible. Check with `datagrant policy check`.
5. Optional: set up a receipt sink. See [operations](../operations.md#external-receipt-sink-v020) and the [CLI reference](../cli.md#receipt-sink). With no sink configured, receipts behave exactly as in v0.1.0.

## Requirements

Python 3.11+, Postgres (CI tests 16), and `pgcrypto` for hash masks. No new dependencies.

## Known limits

- Identity is not authentication: `--as-user` and OS user names aren't verified.
- Hashes are still linkable within one scope, and anyone with the hash key file can recompute them.
- A grantee knows every visible row matched the filter, even on a hidden filter column.
- NULL stays NULL under `partial` and `hash`; `partial` keeps the length.
- Receipts not yet delivered to the sink can't be checked off-host; in `best-effort` mode they can be deleted before `receipts push` runs. The sink is only as trustworthy as its receiver.
- The sink token lives in the environment.
- On Windows, the receipt log, the file sink and outbox flushes aren't locked; run one writer at a time.
- Symlinks are refused for the final path component of key, log, cursor and sink files, but parent directories are followed.
- Disable statement logging for the admin role.
